> Only raise an issue you are confident is a real defect. This is a generated Django migration; most of it is boilerplate. Judge it against the deploy, not against general Python style.

#### Deploy Compatibility

Each new container runs `migrate_multi` on start (`docker/start_migrate`) while the previous release is still serving requests, so every operation must be correct against both the old and the new code.

- A `NOT NULL` column added without a DB-level default. Django's `AddField` drops the default afterwards, and the running release's inserts omit the column. Add it `null=True` or keep a DB default
- A column or table removed, or renamed, in the same deploy as the code that stopped using it. The old release still selects it; this needs two deploys
- A new unique constraint on a column the old code still writes duplicates into
- A `UUIDField(default=uuid4, unique=True)` added to an existing table in one `AddField`. Django evaluates the default once, so every existing row gets the same value and the unique index fails. Add it nullable, fill it with `RunPython`, then make it unique (see `opportunity/migrations/0098_*` and `0099_*`)

#### Secondary Database

`migrate_multi` applies every migration to the primary and, when configured, to a secondary database that receives its rows through logical replication.

- A `RunPython` or `RunSQL` that writes rows without `hints={"run_on_secondary": False}`. On the secondary the rows arrive through replication, so writing them there as well duplicates or conflicts with them. Schema-only operations need no hint

#### RunPython

- Missing `reverse_code`, or `reverse_code` that silently does nothing where a real reverse is possible
- Models imported at module level instead of through `apps.get_model` inside the function, which breaks the historical model state
- An unbounded `.all()` loop or a `.save()` per row over a table that is large in production (`UserVisit`, `CompletedWork`, `OpportunityAccess`, `Payment` and the form tables). Use `.iterator()` with batched `bulk_update`, or a single `UPDATE`
- A data migration that mutates existing rows is a human decision in this project. Flag it for explicit sign-off

#### Locking

- `AddIndex` on a table that is large in production without `AddIndexConcurrently` and `atomic = False`
- `AddConstraint` adding a `CHECK` or `FOREIGN KEY` to a large table, where `AddConstraintNotValid` followed by `ValidateConstraint` avoids the full-table scan under lock
- A column rewrite on a large table: a type change, or a default that Django applies by backfilling

#### Audit Triggers

- Hand-edited SQL in a `pgtrigger` `AddTrigger` or `RemoveTrigger` operation. These are generated from the `@pghistory.track` decorators; the fix is to change the decorator and rerun `makemigrations` (`docs/audit-history.md`)

#### Do Not Report

- The `# Generated by Django` header, field ordering, or anything else the autogenerator produced
- `AddTrigger`/`RemoveTrigger` operations appearing alongside a field change on a tracked model. Changing a tracked model's fields regenerates its triggers
- Missing tests, docstrings or comments. Migrations are excluded from ruff and the pre-commit hooks
